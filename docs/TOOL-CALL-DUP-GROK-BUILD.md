状态：已实施（方法 2–4）　日期：2026-11-04 (UTC+8)

本文件供 **Grok Build / GrokZen 工作区**接续；网关侧只读对侧文档即可。

## 1. 问题（两侧共用结论）

两会话 `01a1a463-…`、`01a1a46e-…` 中，同一 assistant 消息内堆有**相同 `(name, arguments)`、不同 `call_id`** 的多条工具调用（最多约 8 条/组），正文还残留原始 `function=` XML；`events.jsonl` 的 `tool_started` 与结构化调用一一对应 → **真实执行，非渲染重复**。

- **根因**在网关/上游参数流损坏后的模型重发（方法 1，见对侧文档）。  
- **本侧缺的是纵深防御**：同轮不去重、副作用不闸、正文 XML 原样展示。

## 3. 方法 2 — 同轮去重

### 3.1 行为

同一轮 assistant 的 `tool_calls` 列表内，按规范化键 `(name, arguments)` 去重：

- **保留第一次**出现的 `call_id`，后续完全相同键的调用**不派发、不写入可执行队列**；  
- 丢弃项在 UI/notice 记一条（如 `deduped tool_call ×N: name`），便于对照会话；  
- **不**跨轮去重；**不**对 `arguments` 做语义合并（仅字符串级或解析后 JSON 规范化二选一，需固定并测）。

`arguments` 规范化建议：先 `serde_json` 解析，成功则用规范化 JSON 字符串作键；失败则用原始字符串（与 `sanitize_tool_arguments` 失败路径一致），避免把「坏参数」和「好参数」误合并成一条不可追溯的调用。

### 3.2 落点（本仓）

| 层 | 路径 | 做什么 |
|----|------|--------|
| 历史/落盘入口 | `crates/codegen/xai-grok-shell/src/session/storage/mod.rs` `ChatReducer::on_tool_call` | push 前查重；重复则跳过 push 并计数 |
| 采样→会话 | `crates/codegen/xai-grok-sampling-types/src/conversation/responses.rs` `response_to_conversation_items` | FunctionCall 批内按键去重（防上游多 item） |
| 派发前最后一道 | `crates/codegen/xai-grok-shell/src/session/acp_session_impl/tool_calls.rs` | 执行批 `Vec<ToolCallResponse>` 派发前去重（与权限/并行批同一入口） |

实现时以**派发前**为必选，storage/responses 为可选加固；至少保证 **UI 显示的条数 = 实际执行条数**，且二者都已去重。

### 3.3 验收

- 构造同一消息 3 条相同 `read_file` 参数 → 只执行 1 次，`tool_started` 计 1；  
- 同消息不同参数的并行调用全部保留；  
- 回放两会话形态（同参 ×8）→ 新会话重复组为 0。

## 4. 方法 3 — 副作用工具执行闸

### 4.1 行为

对**有副作用或可并行放大**的工具，在本并发批（及可选：本会话短窗口）内：

若已存在**完全相同规范化参数**的调用正在执行或刚完成，则**跳过**后续相同调用，返回明确 skip 结果（例如 `duplicate of call_<id>, skipped`），而不是再跑一遍。

优先名单（与两会话一致，可再扩）：

- `monitor`  
- `run_terminal_command`（尤其 `block_until_ms=0`、`Start-Process`、`schtasks`、杀进程类）  
- 会创建后台任务的 `spawn_*` / 任务类工具（若有）

只读工具（`read_file`、`search_code` 等）**可不闸**：重复执行无状态副作用；是否闸由方法 2 负责降噪即可。

### 4.2 落点

- 派发入口：同 `tool_calls.rs` 批执行前，按工具 taxonomy 标记 `side_effect` / 配置白名单；  
- 并行去重键与方法 2 共用，避免两套规范化。

### 4.3 验收

- 同批 8 条相同 `block_until_ms=0` 启动 → 仅 1 条真启动，7 条 skip；  
- 图 3 形态「两分钟后检查分类进度」×N → 仅 1 个监控/计划任务；  
- 不同参数的合法并行（查不同 PID）不受影响。

## 5. 方法 4 — 展示层折叠正文原始 tool_call XML

### 5.1 行为

assistant `content` 中字面出现的：

```text
function=...
tool_call>...
```

- **默认折叠**为一行摘要（工具名 + 参数首字段），不展开成多行可点调用；  
- 若与本消息结构化 `tool_calls` **同名同参**，标注「与结构化调用重复，已忽略执行」，**绝不**因正文 XML 再次派发；  
- 若仅有 XML、无结构化调用：可提供「解析为调用」的显式动作（默认不自动执行）。

### 5.2 落点

- 渲染：`crates/codegen/xai-grok-pager` scrollback / session_event 相关 block（正文按 content 渲染处）；  
- **不要**在渲染层静默删历史 JSON——只影响展示；执行去重已在方法 2/3。

### 5.3 验收

- 图 2 形态正文：UI 不再刷 8 行原始 XML；  
- 结构化调用仍按 2/3 的结果只执行一次；  
- 桌面与窄屏布局下折叠行可读、可展开。

## 6. 建议实施顺序（本侧）

```text
批次 A（止血，推荐先合）：方法 3 + 方法 2
  └─ 共用 (name,args) 规范化 + 派发前去重/闸 + 单测/会话回放
批次 B（体验，随时）：方法 4
  └─ 纯 UI，不依赖 A 的内部 API 也可先做
批次 C（联测）：对侧方法 1 合入后
  └─ 用 §故障签名 做端到端；确认新轮同轮重复 = 0
```

**与网关：A/B 均可与方法 1 并行开发、独立合入；仅批次 C 需要两边版本都就位。**

---

## 7. 故障签名与证据（两端共用口径）

| 签名 | 含义 |
|------|------|
| 同轮相同 `(name,args)` 多 `call_id` | 重复已进历史（方法 2/3 的靶） |
| `missing field` / `{}` / 参数键后 EOF / 值中换行 | 参数流损坏（方法 1 的靶） |
| content 含字面 `function=` | 正文 XML（方法 4 的靶；1 也可减轻） |
| `tool_started` 条数 = 重复结构化条数 | 已真执行，非 UI bug |

会话证据路径见对侧文档 §5。

## 8. 明确不在本侧

- 改写/合并上游 SSE、AxonHub 转发、8471 行为 → 方法 1，网关工作区。  
- 本侧**不要**用「修复参数字符串」代替去重：坏参数进历史后下一轮仍会放大；去重与闸必须在**派发生效前**完成。

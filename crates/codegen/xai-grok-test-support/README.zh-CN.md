# xai-grok-test-support

grok-build 各 crate 共用的测试基础设施：模拟 inference server、SSE wire-format 生成器、ACP stdio 客户端、无头运行器，以及共用的 `TestSandbox` 文件系统/环境和 `TestProcess` 子进程所有者。PR3 只负责测试子进程；生产环境的 spawning、leader 协议和启动行为保持不变。该基础设施由 `xai-grok-shell` 集成测试、`xai-grok-pager-pty-harness`（`ContentController`）和 `xai-grok-sampler` 测试使用。

> **新鲜度规则：**修改 `src/` 的同一个 PR 必须同时更新此 README——审阅者应将只有 `src/` diff 而没有 README diff 的变更视为不完整。

如何测试的发现说明位于 pager PTY harness crate（`xai-grok-pager-pty-harness`）中。本文件是共用 test-support surface 的 API 参考。

## 模块地图

| 模块 | 提供内容 |
|--------|------------------|
| `inference_override` | 所有 inference 路由共用的类型化请求匹配和响应优先级：endpoint + foreground/auxiliary 分类、具名 expectation 状态、重叠重复请求的 fingerprint 重放、每个 expectation 的 barrier、兼容 FIFO dispatch、auth 拒绝和兼容完成门策略。该模块为 crate-private；只重新导出 `InferenceEndpoint`、`InferenceRequestMatcher` 和 `InferenceExpectation`。 |
| `mock_server` | `MockInferenceServer`——在 `127.0.0.1:0` 提供 `/v1/chat/completions`、`/v1/responses`、`/v1/messages`、`/v1/models`、`/v1/settings`、`/v1/user`。`/v1/models` 条目是 `MockModelEntry`（为 PTY 测试重新导出为 `MockModel`）：`new(id)` / `with_agent_type(id, ty)`，以及可链式调用的 `with_api_backend`、`with_supports_backend_search(bool)` → `supportsBackendSearch`、`with_supports_reasoning_effort(bool)` → `supportsReasoningEffort`、`with_reasoning_effort(&str)` → `reasoningEffort`、`with_reasoning_efforts(Vec<Value>)` → `reasoningEfforts`（原始选项表/裸字符串）；所有值都在顶层输出，供 `parse_remote_model_value` 读取。Inference 优先级是 **matched expectation > compatibility FIFO > required-auth > echo/fixed mode**。使用 `expect_response(name, InferenceRequestMatcher::{foreground,auxiliary}(InferenceEndpoint::{ChatCompletions,Responses,Messages}), ScriptedResponse)` 或 `expect_response_blocked` 注册唯一名称的响应；注册时重复名称会失败，请求会原子地认领一个匹配的 expectation。重叠的重复请求按 endpoint、request kind、非空 `x-grok-req-id` 和序列化请求体构成的确定性 fingerprint 重放；工具结果 follow-up 会复用 turn id 但改变请求体，因此认领下一个 expectation。生产代码没有显式的 HTTP attempt/model-call identity，所以不会根据计时推断已完成的顺序重试：活动的共享调用 settle 后，相同请求会认领下一个 expectation。foreground 请求通常带有非空的 `x-grok-turn-idx`；非 turn 且非空的 `x-grok-req-id` 即使使用工具也属于 auxiliary；空 header 则落入 2+ 工具的兼容启发式。返回的 `InferenceExpectation` 提供由 watch 支持的 `wait_received`、`wait_blocked`、`release`、`wait_satisfied`、`is_satisfied` 和 `assert_satisfied` 生命周期操作。`release` 只打开 barrier；response-body/stream 所有的 RAII 只有在 primary 穿过 terminal 且所有活动的重叠副本 settle 后才发布 `Satisfied`。Primary cancellation 会清理但不产生 satisfaction 或 replay retention，丢弃 handle 会安全释放阻塞工作。Echo（默认）会输出 `Echo: <last user message>` 流，fixed mode 通过 `set_response(text)` 精确重建字节。构造器（`start`、`start_with_models`、`start_with_required_auth`）返回 `anyhow::Result`。Settings 在设置前返回 404（`set_settings(impl Serialize)`，`preset_allow_access()` 对应 `{"allow_access": true}` gate）；scripted `/v1/settings` one-shot（`enqueue_response`）优先于稳定状态值（用于 stale-snapshot 测试）。`/v1/user` 提供最小 `UserInfo`，其 `subscriptionTier` 由 `set_user_subscription_tier(Option<&str>)` 控制（`None` = free）；日志条目保留 query string（例如 `/v1/user?include=subscription`），因此可以计数 subscription-check cadence。请求日志：`requests()`（`LogEntry`，包含 body、`authorization`、完整 POST headers 以及 `header(name)` accessor）、`request_bodies()`、`request_count()`、`has_chat_completion_request()` / `has_responses_request()`（逐 endpoint 精确匹配）、`messages_request_count()`、`last_system_prompt()`、`request_log_summary()`。**Storage：**`POST /v1/storage` 支持可切换的 401（`set_storage_unauthorized`）；接受的上传通过 `storage_uploads()` → `StorageUpload { path, size, body, authorization }` 获取（`body` 最多保留 256 KiB，超过则为空；`authorization` 是原始 header）。**Privacy：**`PUT /v1/privacy/coding-data-retention` 模拟 cli-chat-proxy 的成功路径——返回 200，并回显请求中的 `codingDataRetentionOptOut` 布尔值，像每条路由一样记录日志（privacy-banner e2e）。运行时开关：`set_models`、`set_messages_stop_reason`。丢弃时关闭。 |
| `scripted` | 仅数据型响应 body（公共 surface 不暴露 axum 类型）：`SseEvent { event, data }`（`::data`、`::with_event`）、`ScriptedBody::{Json, Sse, Raw}`（`Raw` = 可控制字节的畸形 SSE）、`ScriptedResponse { status, headers, body }`（`::sse`、`::json`、`::text`）。Inference 调用优先使用请求匹配的 expectation；`enqueue_response(path, response)` 仍是每个 path 的兼容 FIFO，并继续用于 `/v1/settings` 等非 inference one-shot。Scripted SSE 遵循 `set_chunk_delay`；匹配的 JSON、raw、SSE，甚至空 SSE body 都遵循每个 expectation 的完成 barrier。兼容的 `hold_agent_completions` gate 也覆盖三个 inference endpoint 上的 foreground scripted SSE。校验会提前进行——注册时错误的 status/header 会 panic。 |
| `sse` | 三种 wire format 的 event-list 构建器：`chat_completion_events` / `responses_api_events` / `messages_api_events(text, model, stop_reason)`（echo 风格，会折叠空白），以及字节精确的 axum 变体 `chat_completion_events_exact` / `responses_api_events_exact` 和对应的公开 scripted 变体 `chat_completion_script_exact` / `responses_api_script_exact`（messages 天然为 single-delta，字节精确）。exact/echo 分离是关键契约——详见模块内的字节精确测试。还提供返回 `SseEvent`（用于 `ScriptedResponse::sse`）的 scripted-scenario 构建器：`responses_api_reasoning_only_events(reasoning, model)`——reasoning summary delta 在没有 message/output-text 的情况下以 `reasoning` item 完成，使 shell collector 将该轮分类为 `EmptyReason::ReasoningOnly`（model-doomloop trigger）；`responses_api_reasoning_and_text_events(reasoning, text, model)`——先发 reasoning delta，再发普通文本回答（普通 reasoning-model turn）；`responses_api_reasoning_then_tool_call_events(reasoning, call_id, name, arguments, model)` 及其 Chat Completions 对应项 `chat_completions_reasoning_then_tool_call_events(...)`——先发 reasoning delta，再发一次工具调用（think-then-call turn，工具调用完成思考，使该轮保持非空）；doom-loop 检查三件套：`responses_api_doom_loop_check_events(triggers, reasoning, model)`——注定失败的 reasoning-only turn，按 `triggers` 的累计前缀重新发送带有命名 `response.doom_loop_check` 的 frame，并在 `response.completed` 上附带终结的 `doom_loop_check.triggers` 副本；`responses_api_doom_loop_terminal_only_events(triggers, reasoning, text, model)`——普通回答，仅 terminal response 携带该字段；`responses_api_with_doom_loop_frame(check_frame_data, reasoning, text, model)`——将调用方提供 payload 的一个命名检查 frame 拼接到普通 turn 中（字节精确的 `xai_grok_sampling_types::doom_loop::SAMPLE_CHECK_EVENT_DATA{,_CUMULATIVE}` fixtures 或畸形变体）。 |
| `sandbox` | `TestSandbox`——临时根目录、隔离的 `HOME`/`USERPROFILE`、显式的 `GROK_HOME`、workspace 和 `TMPDIR`/`TMP`/`TEMP` 的单一所有者。子命令使用 `env_clear()` 加最小平台 allowlist、loopback `NO_PROXY`、interactive-git 抑制，以及 telemetry/feedback/trace/instrumentation/updater kill switch；不带 ambient leader socket 或 proxy 变量。Unix 在设置时保留宿主 `SHELL`，否则回退到 `/bin/sh`；显式 override 仍优先。`TestSandbox::builder().mock_url(url)` 会连接 grok API/models/auxiliary endpoint 和 fake CI key；`.git()` 会初始化并提交所拥有的 workspace。直接执行 Git 的 Bazel 测试目标提供 `@git_hermetic` runfiles 和 `GIT_BIN_PATH`；构造时 `TestSandbox` 在仍是 Bazel execroot 的 parent cwd 中解析该路径，保存绝对的 `GIT_BIN_PATH`/`GIT_EXEC_PATH`，并将 binary parent 加到基线 `PATH` 前面。`TestSandbox::git_command()` 应用该清理后的环境以及 detached、non-interactive Git 设置。没有 `GIT_BIN_PATH` 时保留普通基线 `PATH`，不添加特殊 binary/exec 变量。`set_env`/`extend_env`/`remove_env` 是基线之后的窄范围 override seam。`diagnostic_summary()` 会隐藏 credential-key segments/suffixes 以及所有 malformed/non-loopback endpoint；loopback URL 会被解析并移除 userinfo/query/fragment。 |
| `process` | `TestProcess`——构建在 `TestSandbox` 之上的 canonical Tokio child owner：清除/重新应用 sandbox env，应用 `pager_env`，强制 null/piped stdin 策略，分离 TTY，拥有 PR3 之前的 `xai_tty_utils::ProcessGroup`，并捕获有界 stdout/stderr 尾部。Unix 分离会在 exec 前建立子进程 session/process group；Windows 保留 `CREATE_NO_WINDOW`，并使用现有的尽力而为 post-spawn Job attachment，不声称原子性的 descendant containment。私有 Unix `waitid(WNOWAIT)` 观察退出，以便在 PID/PGID 重用前清理 descendants。`wait_with_deadline` 不具破坏性；Unix `close` 发送 SIGTERM 后升级，Windows 使用立即 Job hard-kill 策略；Drop 会同步 kill 并执行有界、尽力而为的 reap。reap 后 PID 不可用；status/reason、截断计数器、读取/生命周期错误和经过 secret-sanitized 的尾部会被缓存。`TestProcessTree` 是为保留其具体 child 的依赖提供的 process-tree adapter。所有生命周期策略都只用于测试；生产 utility 行为和 API 未改变。 |
| `acp_client` | `GrokStdioClient` 通过真实 pipe，经由 `agent-client-protocol` 驱动 `grok agent stdio`：`spawn` 创建 sandbox，`spawn_with_sandbox` 在重启间复用一个 sandbox，`spawn_with_sandbox_env_and_args` 增加显式 env/global-argument override。它提供 initialize/authenticate、session create/load、prompt、`*_with_timeout` wrapper、child PID、捕获的文本/stderr、进程诊断、显式 close/kill signal，以及 `take_sandbox`。`RawStdioClient` 是 escaped-slash 方法和 string UUID id 的 raw-wire sibling：精确 id 的响应匹配会跳过 notification，自动以 `-32601` 拒绝 agent→client 请求，并在超时时报告跳过的流量。两者都会在 `TestProcess` 拥有 child tree 和 pipe-tail 诊断期间保持 sandbox 存活。 |
| `headless` | `run_headless[_with_env]` 使用所拥有的 canonical `TestSandbox` 运行 grok；`run_headless_in_sandbox[_with_env]` 拥有传入的 sandbox，而 `run_headless_in_sandbox_borrowed[_with_env]` 保持其可用以检查 artifact。`_with_env` 变体在 hermetic baseline 之后应用显式的 last-wins override。`TestProcess` 拥有生命周期和超时 tree-kill；按比例缩放的 60s 进程 deadline 之后，另有独立且有界的 2s pipe-drain budget；保留 pipe 或 read-task 失败会返回有界的部分尾部。所有变体返回 `HeadlessResult { status, stdout, stderr, timed_out, elapsed }`。断言 helper 是 `assert_headless_success`、`assert_no_crashes` 和 `stderr_tail`。 |
| `env` | 二进制解析（`grok_binary()`：`GROK_BINARY` → `CARGO_BIN_EXE` → 本地 debug build）和 `git_workdir()`，后者返回已初始化 git 的 `TestSandbox`；使用 `.workspace()` 获取 cwd。 |
| `leader` | 仅 Unix 的 `LeaderFixture` 对每个 `LeaderStdioClient` 都是必需的。它只拥有一个具体的初始 leader 以及它直接 spawning 的 client 对象。调用方先关闭/丢弃 client；`LeaderFixture::close` 会拒绝活动 client，并只对初始拥有的 child/group 执行有界 TERM→KILL→reap。如果正常和硬式 client 清理都失败，测试专用的 unwind containment 路径会请求 hard kill，并在发出 signal 后有意泄漏保留的 client/leader owner；这样可在 panic unwind 期间保持所有权，且受测试进程生命周期限制。锁文件 PID 仅用于观察：不会采用或 signal 已分离的 replacement generation。会产生 detached replacement 的 death/re-election 和 version-skew 场景仍标记为 `leader-acceptance` ignored/manual，并保留跟踪说明，直到 OS containment 或仅测试的 leader binary 可以拥有整条 generation chain。生产环境不需要 marker/protocol/bootstrap 行为。 |
| `uds_proxy` | 仅 Unix 的 `UdsProxy`——面向 leader IPC socket 的、了解 frame 的（4-byte BE length prefix）man-in-the-middle。`UdsProxy::spawn(proxy_path, upstream_path, FaultPlan)`；`FaultPlan { direction, drop_frame, sever_mid_frame, delay, duplicate_frame }`（每个 connection、每个 direction 的 1-based frame index）；运行时 `FaultHandle::sever_now()` + `forwarded(direction)` 计数器；frame body 上限为 64 MiB（与 leader-transport 一致——损坏的长度会报错而不是分配内存）。不会改变生产代码：将 `LeaderClient::connect` / `GROK_LEADER_SOCKET` 指向 proxy 路径即可。 |

## Sandbox 契约

- `TestSandbox` 至少要与所有使用其路径的 child 同时存活。
- builder 只用于构造时的 endpoint/git 选择。测试专用 flag 和 terminal brand 使用 `set_env`/`extend_env`；最后的显式 override 胜出。使用 `remove_env` 测试变量不存在的情况。
- 不要添加进程全局的 env mutation。文件系统/环境所有权留在 `TestSandbox`；process group、job、输出尾部和 kill-tree 所有权留在独立的 `TestProcess`/`TestProcessTree` harness。
- 诊断可以显示 sandbox 路径和经过清理的 HTTP(S)/WS(S) loopback URL。URL 解析采用 fail-closed：移除 userinfo/query/fragment，同时隐藏 malformed 或非 loopback 值。类似凭据的 key segments/suffixes 始终隐藏。

## 添加能力

**响应模式**（`mock_server.rs`）：扩展私有的 `ResponseMode` enum，并添加 setter；将新 arm 接入**三个** inference handler（每条 route 中的 match）；scripted response 仍须胜出。扩展 crate 内测试：新模式的 HTTP round-trip，加上 `scripted_responses_serve_fifo_per_path_then_fall_back` 中证明 fallback 到达该模式的一段。echo 固定测试（`echo_mode_echoes_last_user_message`）必须原样通过——echo 字节是冻结的。

**wire format**（`sse.rs`）：添加 echo 风格 builder；如果 client 会逐字节重建文本，再添加基于 delta fn 的 `_exact` 变体；然后在 `mock_server` 中添加 serving arm（所有模式），如果是新 endpoint 还要添加 route。扩展字节精确 pin：`deltas_reconstruct_multiline_response_byte_for_byte`、`deltas_preserve_runs_of_whitespace`——它们是确保 fenced code block（mermaid）在流式传输中保留的契约。**scripted-scenario builder**（用于表达 echo/fixed 模式无法表达的特定 completion，例如 `responses_api_reasoning_only_events`）应改为返回供 `ScriptedResponse::sse` 使用的 `SseEvent`，不需要 `mock_server` mode wiring，并附带断言其 event shape 的模块内测试。

**expectation matcher**（`inference_override.rs`）：保持公开 matcher 类型化且范围窄。在 serving 前于单一 expectation-state mutex 下 claim，只按 model-call fingerprint 重放重叠的活动副本，并为 auxiliary non-consumption、并发单 claim 行为、生命周期 barrier 和有用的 unsatisfied 诊断添加聚焦测试。Expectations 和 compatibility script 必须保持在 required auth 和 fallback mode 之前。

**scripted-body kind**（`scripted.rs`）：添加新的 `ScriptedBody` variant + `into_response_paced` 中的 render arm；如果数据可能无效，在 `validate` 中做提前检查。添加断言 client-visible bytes 的 crate 内测试（`Raw` 的字节精确测试是模板），为新 body 测试 terminal gating，并保持 `scripted_response_takes_precedence_over_required_auth` 为 green——优先级属于契约。
